# Start a new project with Claude Code

> A step-by-step setup for a fresh project: lean context, clear instructions, fewer surprises.

## What you'll set up

Starting a project is the best moment to set Claude Code up well. A few minutes now saves tokens, permission prompts and repeated explanations in every session after. You'll pick a model, write a strong first prompt, create a short CLAUDE.md, add sensible settings, and check the result in this dashboard.

Reading time: about 8 minutes. Tick the boxes as you go.

## Step 1: Before you start

Install Claude Code (or check that it's there), then start it from your project folder. Claude reads the folder you start in, so always launch from the project root.

```bash
curl -fsSL https://claude.ai/install.sh | bash
claude --version
cd /path/to/my-project
claude
```

On Windows PowerShell, use `irm https://claude.ai/install.ps1 | iex`. Native installs update themselves in the background; Homebrew and WinGet installs need a manual upgrade.

Now pick your **model and effort at the start**. Each model has its own prompt cache, so switching models mid-session makes the next request re-read the whole conversation uncached. On many setups, changing effort does the same. You can set both when you launch:

```bash
claude --model opus --effort high
```

Or use `/model` and `/effort` right after starting. The default effort (`medium`) is fine for everyday features; raise it for tricky bugs. More on this in [Change mid-session or start fresh?](#/guides/change-or-restart.md).

- [ ] Ran `claude --version` and started `claude` in the project root
- [ ] Chose model and effort before the first real prompt

## Step 2: Describe the project in your first prompt

Claude can read code, but a new project has almost none. It can't see your goals, your preferences or what you consider finished. Tell it up front. The points that help most:

- **Goal and users**: what you're building and for whom.
- **Tech stack and versions**: language, framework, database, package manager.
- **How to run, build and test**: even if the commands don't exist yet, say which tools you want.
- **Folder structure**: where code, tests and docs should live.
- **Coding conventions**: style, naming, error handling, libraries to prefer.
- **What "done" looks like**: tests pass, the page loads, the endpoint returns the right data.
- **What NOT to touch**: generated files, secrets, folders that belong to someone else.

Copy, fill in and paste this template:

```text
I'm starting a new project. Here is the context:

Goal: [one or two sentences: what it does and who uses it]
Stack: [e.g. TypeScript 5, Node 22, Fastify, PostgreSQL 16, pnpm]
Run / build / test: [e.g. pnpm dev, pnpm build, pnpm test with Vitest]
Structure: [e.g. src/ for code, tests/ next to it, docs/ for notes]
Conventions: [e.g. small functions, no default exports, errors via src/lib/errors.ts]
Done means: [e.g. tests pass, lint is clean, README explains how to run it]
Do not touch: [e.g. .env files, the vendor/ folder]

First, set up the project skeleton with a working test command.
Ask me questions if anything is unclear before you start.
```

Not sure about the details yet? Ask Claude to interview you: "Interview me until you could write the spec, then write it to SPEC.md." Then start a fresh session to build from that spec.

- [ ] Wrote a first prompt covering goal, stack, commands, conventions and "done"
- [ ] Listed what Claude must not touch

## Step 3: Create CLAUDE.md with /init, then trim it

Once there's some code, run `/init`. Claude scans the project and writes a starting `CLAUDE.md` with build commands, test instructions and conventions it finds. If a file already exists, it suggests improvements instead of overwriting.

```text
/init
```

Then edit. The work is mostly **removing lines**.

- **Keep**: exact commands (install, test, a single test file, lint, typecheck), conventions Claude can't guess, and gotchas.
- **Leave out**: things Claude can learn from the code, long procedures (make them skills), and rules that must never be broken (use a hook or deny rule).
- **Keep it short**: the official guidance is under 200 lines per file. Every line loads into every session.

A good example:

```markdown
# Project
Recipe-sharing web app. Users save, tag and search recipes.

# Commands
- Install: pnpm install
- Dev server: pnpm dev
- All tests: pnpm test
- One test file: pnpm vitest run path/to/file.test.ts
- Lint and typecheck: pnpm lint && pnpm tsc --noEmit

# Conventions
- TypeScript strict mode, no `any`
- API handlers live in src/api/, one file per resource
- Throw errors with helpers in src/lib/errors.ts, never raw strings
- New features need a test in the same folder

# Gotchas
- Tests need DATABASE_URL, copy .env.example to .env
- src/gen/ is generated by `pnpm codegen`, never edit it by hand
```

Note: edits to CLAUDE.md apply after `/clear`, `/compact` or a restart, not in the running session. For personal notes, use `CLAUDE.local.md`. More in [CLAUDE.md and memory](#/guides/03-claude-md-memory.md).

- [ ] Ran /init and reviewed the CLAUDE.md it created
- [ ] Trimmed it to commands, conventions and gotchas

## Step 4: Settings that pay off

**Permissions.** Allow the safe commands Claude runs all the time, and deny reading secrets. Use `/permissions` in a session, or edit `.claude/settings.json` in the project:

```json
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": [
      "Bash(pnpm lint)",
      "Bash(pnpm test *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)"
    ]
  }
}
```

Settings files are strict JSON: no comments, no trailing commas. Run `/status` to confirm the file loaded.

**Which file to commit?**

| File | Who it affects | Commit it? |
| --- | --- | --- |
| `.claude/settings.json` | Everyone in the project | Yes |
| `.claude/settings.local.json` | Only you, this project | No |
| `~/.claude/settings.json` | Only you, every project | Not in the repo |

Claude Code keeps `settings.local.json` out of git when it creates the file itself. If you create it by hand, add it to `.gitignore`, together with `CLAUDE.local.md` and your `.env` files.

**Status line.** Show how full the context is at all times:

```text
/statusline show model name and context percentage with a progress bar
```

Claude Code writes a script and updates your user settings for you.

- [ ] Allowed test and lint commands, denied `.env` reads
- [ ] Committed `.claude/settings.json`, ignored the local files
- [ ] Set up a status line with context %

## Step 5: Add only the MCP servers and skills you need

Every MCP server and skill adds something to every session. Tool search keeps MCP light (names first, full definitions on demand) and skills load only their description until used, but it still adds up. Start with nothing and add a server only when you keep copying data from another tool into the chat. A good CLI like `gh` is often even cheaper.

```text
/context
/mcp
```

`/context` shows what fills your context right now. `/mcp` shows server status and lets you disable the ones you don't need. Details in [MCP, skills and subagents](#/guides/04-mcp-skills-subagents.md).

- [ ] Checked /context after adding any MCP server or skill
- [ ] Disabled servers I don't use with /mcp

## Step 6: Your first task the efficient way

Use a simple loop for every task:

1. **Plan**: press `Shift+Tab` until plan mode is on, or start a single prompt with `/plan`. Claude reads and proposes, but doesn't edit.
2. **Review**: read the plan. Choose "No, keep planning" to change it, or press `Ctrl+G` to edit it yourself.
3. **Implement**: approve the plan and let Claude make the changes.
4. **Test**: ask Claude to run the test command from your CLAUDE.md.
5. **Commit**: "commit my changes with a descriptive message".

```text
/plan add a recipe search endpoint with tests, following CLAUDE.md
```

When the task is done, run `/clear` before the next one. It costs nothing, and the next task won't keep paying for this one's history. See [Workflows](#/guides/05-workflows.md) for more patterns.

- [ ] Planned, reviewed, implemented, tested and committed one task
- [ ] Ran /clear before starting the next task

## Step 7: Make repeatable things reusable

If you type the same instructions twice, make a skill. Custom commands are skills now: a file at `.claude/skills/<name>/SKILL.md` creates `/name`. Old `.claude/commands/*.md` files still work.

```markdown
---
name: new-endpoint
description: Create a new API endpoint with a test
disable-model-invocation: true
---

Create an API endpoint for $ARGUMENTS:

1. Add the handler in src/api/
2. Add a test next to it
3. Run pnpm test and fix any failures
```

Save it as `.claude/skills/new-endpoint/SKILL.md` and run `/new-endpoint favorites`. With `disable-model-invocation: true`, only you can start it.

For things that must happen every time, use a **hook**. This one in `.claude/settings.json` runs Prettier after every file edit:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
          }
        ]
      }
    ]
  }
}
```

It needs `jq` and Prettier installed. Check it with `/hooks`.

- [ ] Created one skill for a task I repeat
- [ ] Added a formatting hook (optional)

## Step 8: Check your setup in this dashboard

Work a session or two, then open this dashboard and pick the session.

- Look at **System prompt, tools & memory**. This is the fixed cost you pay on every request. If it's large, trim CLAUDE.md or remove MCP servers.
- Look at **Skills, MCP & reminders** to see what your skills and servers add.
- Compare a new session with an older one to see whether your changes helped.

Read [Reading this dashboard](#/guides/06-reading-the-dashboard.md) for a tour of every screen.

- [ ] Opened a session and checked the fixed part of the context
- [ ] Checked the skills and MCP rows
